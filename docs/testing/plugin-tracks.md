# SDD-045 插件双轨验收计划

一条只处理文本的插件和一个能驱动底盘的插件，能否用同一种方式换版？判断依据有三项：新请求去了哪一版、旧操作由谁收尾、现场到底发生了几次动作。本文给测试执行者安排具体试验及证据。P0 交付测试设计。下文标为「计划」的门槛须在实现后逐项取证，历史用例只提供可复用的对照。

准备 soft 用例时先确定由谁维护注册项与调用绑定。准备 physical 用例时还需确定哪一端实际拒绝过期控制指令，独立见证放在哪里。[运行时职责与版本归属](../plugin-runtime-mapping.md) · [物理资源交接与 fencing](../architecture/plugin-physical-handoff.md)

## 3　怎样冻结 v1 的字节

1. 实现前用锁定的 v1 提交生成一套不可由候选运行时重写的基准。包括最小服务、多层依赖、顺序打乱、缺省与显式 `draining:false`、排空、不可用目录和已经绑定的在途任务。分别保存输入原始字节、v1 发布后的声明字节、规范化身份输入、管理器 revision、运行时 binding 及公开返回的 v1 部分。输入手工格式与发布器规范化结果各自与自己的基线比较。
2. 比较时保留编码、换行、字段存在性与排序，固定可变时间、测试端点和身份。直接比较原始输出，报告首个差异的文件、偏移、基线与候选 SHA-256。分别冻结三种身份。v1 发布器会补 `draining:false`，管理器 revision 对排空敏感。Service binding 排除 draining，纳入传递依赖绑定。Tool binding 取 id、version、parameters、effect、endpoint，并在满足条件时加入 outcomes 或 verbatim_argument、utterances。分别用一个普通 Tool、一个声明结果类型的 Tool 和一个接收原话的 Tool 锁定字节。另存镜像内容摘要验证实际加载的实现版本。`agent/plugin_manager.py` · `agent/runtime_plugins.py` · `agent/planning.py`
3. v2 展示字段或健康采样的新增须走新契约投影。分别测试「旧声明→新读取器」「旧账本/在途操作→新读取器」「新元数据→旧消费者的兼容投影」及回退后读旧数据。对使用严格字段集的 v1 接口比较整个公开响应。新投影另检增量字段，阻止新字段反写 v1 本体。若 v1 读取器面对原生 v2 必须拒绝，记录明确拒绝和旧状态保持。预期哈希由旧代码或审阅过的固定字节计算。

## 4　冻结任务集与独立计量

建基线前冻结任务 ID、自然语言原文、输入快照、场景种子、机器人/模型版本、允许操作及最大次数、超时、故障和独立成功判据。覆盖纯软件确定性结果、只读传感、物理到点并停车、缺依赖、应拒绝、已执行后回执丢失及未知结果。基线与候选使用相同起始状态，每组分列正常/故障、soft/physical、仿真/工位。保存每一项原始分子/分母。冻结后新增样本另开版本，保留失败轮次。`tests/system_suite.py`

| 指标 | 计数方法与独立证据 | 判定 |
|---|---|---|
| 误报成功 | 分子为系统宣称成功，而文件字节、独立 verifier、外部测距/停稳观测给出失败的任务数。分母为全部系统宣称成功且有独立判定的任务数。成功但缺证单独计为「未验证成功」 | 误报数及未验证成功数均须为 0。成功分母须非零；另报告各类任务覆盖和正确拒绝 |
| 重复物理动作 | 按资源与逻辑 operation ID 关联控制器接受记录和外部编码器/位姿时序。对每个操作求 `max(0, 实际独立动作次数 − 清单允许次数)`，总和为分子。分母为参加试验的不同物理操作数。持续动作按预先冻结的起动/终止规则划段，避免把速度帧计作多次动作。用外部时序捕获没有 operation ID 的意外动作，另记未授权数 | 重复数为 0，且处理失联/重投场景的分母非零；未授权动作必须为 0 |
| 任务完成度 | 对期望成功的冻结任务，用独立判据通过数除以该类全部预置用例数，失败、超时、未知都保留。应拒绝的任务按正确拒绝数/预置拒绝数另报 | 与逐例基线对照，任何此前通过而本次退化的项都须修复并重新验收；禁止通过全拒绝获得安全指标 |
| 生命周期证据覆盖 | 分母取独立注入器预先登记且实际发生的生命周期动作数，分子取可沿源身份、版本、摘要和结果唯一对齐者。重复传输和派生通知分别列出 | 所有必测阶段有来源。无法取证为证据缺口，不能用插件自报再证明它自己 |

## 5　物理工位与回退

物理故障用例核对的是实际拦截点。两位所有者争用同一资源预期得到 `plugin.lease_conflict`；旧租约持有者在交接后迟到的指令预期得到 `plugin.fence_rejected`。停稳证据缺失、交接未确认、验收器身份或结果无效分别核对计划中的 `plugin.stop_unconfirmed`、`plugin.handoff_unconfirmed`、`plugin.verifier_invalid`。保留 Gateway/Core 的原始错误码与 cause、原操作号和采样时间，并用控制器及外部见证检查动作。以上为拟验收的错误语义。

先在无设备的隔离容器验证软件门禁，再做 Gazebo 动力学演练，最后用实物平台在独立工位验证。工位先验证物理急停和限速，轮式平台可先架空车轮。每种执行器记录资产身份、固件、控制帧与时间域，冻结停车速度阈值、最短稳定窗口、观察频率及允许的命令到停稳延迟。外置编码器、标定过的独立摄像机或测距仪负责计数及停稳。丢弃执行回执和断开执行器反馈分别进行，核查零重复、独占交接和人工复核入口。无实物时填「未测」，QEMU 的 ARM64 结果只代表指令集与容器兼容。

触发回退的条件包括误报成功、重复物理动作、未经授权的控制、绑定漂移、无法确认停稳和 v1 基准字节变化。先停止接收新操作、暂停自动重试，保留原操作号和原始证据。待执行器所有者确认停稳并明确是否已生效，再恢复上一受验声明、依赖版本、镜像和可读账本。在途效果未知时保持待核查并给出操作员的核对项。回退验收重新验证原绑定、新请求、无关任务、传感器状态与零额外动作。`docs/rover-commissioning.md`
