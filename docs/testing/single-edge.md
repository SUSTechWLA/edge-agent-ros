# 单台 Edge Agent 的系统测试与架构评价

读完本页，应能判断三件事：一次“成功”有没有物理证据，改一处代码需要验证哪些使用方，以及哪些问题必须带到板卡和底盘上测。

如果需要先判断本版能否进入上板联调，可看 18 项本地验收、五轮制动和八组资源限额的对照，其中保留了两次内存耗尽的失败样本。[本次单机实测记录](sdd-003-results.md)

## 一台机器人怎样证明任务完成

对同一台轮式机器人，分别下发“只规划到庭院的路线”和“去庭院巡检”。第一条选择只读工具 `preview_route`，把当前融合定位、室内外区域、经过的门口、地图版本和路径距离交给用户。第二条选择 `navigate_place`，沿路执行并逐点验收。两者复用同一算法 `Layout.plan`；只有运动工具能提交 ROS 委托。地图别名匹配多处时，系统要求明确地点。受限目标、未定位和断流都有各自的处置。

一次极具区分力的故障是，ROS 内核里已经有一条“在工位停稳”的成功记录，刚好用了新“去庭院”任务的操作 ID。旧版本直接采信该记录，把工位的坐标写成到达庭院的证据。独立 Gazebo 位姿表明当时距庭院约 **3.57 m**。现在首次绑定通过内核的幂等提交接口核对整串点位，冲突返回 `core.id_conflict`。已经确认过的委托如果从内核账本消失，则进入待核查；逐点回执数量、顺序和位置也必须符合原路线。[场景实现](../../scene/provider.py) · [通过公开接口复现](../../tests/system/scene_binding_acceptance.py)

## 模块评价与维护边界

| 模块 | 当前职责、输入和输出 | 可保留的设计，以及值得控制的耦合 |
|---|---|---|
| 任务 Agent / 规划器 | 自然语言、可见工具、模型配置 → 版本化步骤和持久任务 | 模型和固定句式共用工具验证。规划失败、执行失败、结果未知需要分别入账。调整提示优先复测候选工具、实际输入和输出约束；只有改变现场行为时才需要运动验证。 |
| 场景工具 | 名称、融合位姿和有版本的地图 → 候选路线或 ROS 委托 | 读路线与执行路线共用语义和几何，便于换地图。场景插件可独立替换；地图布局既供规划也生成仿真几何，因此改墙、门、净空要连运动验证一起跑。 |
| C++ 执行内核 / 运动网关 | 路点和稳定操作 ID → Action、制动、停稳证据 | 内核持有物理动作授权，网关处理现场传感器；Agent 重试之前须对原操作对账。换控制器要复测取消、心跳中断、停止确认和未知占用。 |
| 感知与控制台 | 带采样时刻和 frame 的 ROS 数据 → 融合状态、地图、快照、回放 | 控制台是观察者。传感器有消息到达、消息的采样时间有效、数据足以更新地图，是三个不同判据。感知字段变更会影响地图前端和现场复盘。 |
| 账本和事件归档 | Agent 与内核事务、插件事件 → 按 ID/游标关联的证据 | 源端分别持有自己的事实，归档可独立恢复。历史库迁移和读旧记录是长期兼容成本。维护稳定错误码、版本和因果 ID；新消费者先接归档接口。 |
| 板端适配 | ROS remap、机体驱动、动作服务、传感器标定 → 同一组上层接口 | Compose 分离仿真 SDK 与板端软件。现有融合、通行几何、前向制动基于二维轮式底盘。接入其他机体需要自己的运动与感知适配，并验证现场制动策略。 |

目前这些边界足以支持围绕工具清单、模型配置、观测订阅的局部迭代。最大的维护成本在**跨进程的一致性**：同一 ID 能否对应同一实际动作、重启后哪份账本拥有终态、不同时间域的数据能否一起使用。此次修复集中在产生或校验事实的模块，保留公开 ROS 服务消息、现有任务入口和旧的 Git 证据。真实模型权重、ROS 传感器时钟、物理制动分别使用各自的验证方法。

### 下一个开发者从哪里改

| 开发任务 | 最小改动路径 | 合入前提供的证据 |
|---|---|---|
| 增加读数类工具，例如读取电量 | 在 `plugins/` 描述参数和结果，由 HTTP 提供者读取对应 ROS topic。登记来源、采样时刻、过期判据和错误码。只有引入新的授权语义才需修改 Agent 内核。 | 没有读数、读数过期、正常读数、重复提交四种结果。任务回放能关联提供者版本和原始采样。 |
| 改模型或提示 | 从 `contracts/` 的配置入口调整，保持已有步骤格式、工具权限和参数约束。将原请求与新方案对照，记录模型及提示版本。 | 纯契约先验加载，随后用实际模型覆盖代表性输入。对于“只规划”“去某地再读数”等请求，逐项断言禁止的副作用与必须出现的步骤。 |
| 修改动作恢复 | 先确定事实归属。Agent 记录意图与原操作 ID，执行内核记录受理和终态，现场提供者记录观测。将任一方缺失、冲突与已证实失败分别建例。 | 老库继续可读；已受理、回执丢失、重启、账本遗失均有判断；物理副作用次数与任务重试次数分别计数。 |

优先保留三处边界：自然语言到工具步骤、步骤到可查询的 ROS 动作、观测到只读回放。当前 `agent/service.py` 同时承载 HTTP、工作线程、任务账本和 ROS 调用。下次多条需求同时改动这一文件时，先沿已有 `Journal`、`Robot` 和 `worker` 的接口分别提取，再用同一输入和故障验证提取前后行为。引入第二种底盘前，先让新适配器通过取消、结果未知和停稳契约。跨机调度需独立设计，不属于本次单机门槛。

## 怎么选测试

完整回归覆盖本仓库已定义的单机行为。PR 默认根据 Git 合并基点与工作树差异选择测试；发布分支、主分支和手动 CI 运行全套。新文件类型、公共 ROS 接口、Compose、构建或测试选择器本身发生变化，默认全选。测试选择是依据已登记的消费关系做的保守估计。新增跨模块调用时，先为下游增加选择规则和反例测试。[规则与回归用例](../../tests/test_selection.py) · [CI](../../.github/workflows/ci.yml)

| 修改例子 | 最少需要回答的问题 |
|---|---|
| 项目说明或需求文档 | 本地链接指向的代码和证据能否在干净检出中找到，规格记录是否完整？文档修改可以跳过仿真。 |
| 模型系统提示或工具诊断文案 | 实际请求使用了哪个版本？错误码和工具契约是否保留？没有模型缓存时，报告单列真实模型跳过原因。 |
| 语义工具提供者 | 能否只规划不动、对账、正确拒绝、离线重传？工具清单变化还会影响模型目录和工作台。 |
| 网关或仿真几何 | 错误扫描会不会产生运动指令？制动后真值是否停稳？取消、断链、完整路线及恢复是否受影响？ |
| 回放、传感器或事件格式 | 老库、冻结/回退的时间、错误 frame、分页和消费者重连能否保留正确状态，UI 能否使用？ |

```sh
# 看当前工作树相对于上次提交的影响；改为目标分支可预览整条 PR
python tests/system_suite.py --changed-since HEAD --plan
python tests/system_suite.py --changed-since origin/main
# 全套仿真；已有本地模型缓存时连真实推理一起验
python tests/system_suite.py --ollama-cache-volume edge-agent-ros_models
```

运行机需要 Python 3.10+、Docker Compose、PowerShell 7。前端用例需要 Node.js 22 和 Chrome/Edge，可用 `CHROME_PATH` 指定浏览器。运行器按需建立独立镜像、ROS 网络、端口、空数据卷和临时浏览器 profile。真实 Ollama 验证从已有卷只读复制模型数据到本次可写卷，启动后先检验 `qwen2.5:1.5b` 是否可用。退出时清理该次运行的测试资源。断电或强杀测试进程时，可以根据该次日志的项目名查找遗留的容器。

## 报告放在哪里

| 路径 | 归属及用途 |
|---|---|
| `docs/specs/SDD-003-simulation-system-tests.md` | 行为与验收约定，随改动更新 |
| `tests/system_suite.py`、`tests/test_selection.py` | 跨平台测试入口、消费关系与测试选择规则 |
| `tests/system/` | 新增的跨服务故障、浏览器与板端软件探针。已有验收脚本的公开路径继续保留 |
| `src/*/test/`、`console/server/test_*.py` | 与模块一起维护的契约和回归 |
| `.ci-results/system/runs/<运行号>/summary.json` | 本次 Git 版本、镜像 ID、运行阶段、时长和结果。同目录保存逐阶段日志、世界轨迹、导出记录和机器可读结果 |
| `docs/evidence/` | 经过核对的有限实测样例，用于评审与复盘 |
| `artifacts/releases/v0.1/`、`artifacts/console/` | 已保留的历史版本证据。日常新测试写入独立运行目录 |

判定故障先读失败阶段的日志，再对照输入、源时间、世界位姿、稳定错误码和终态。看见 `passed_with_skips` 时展开 `stages`。每项高风险变更至少保留一个旧版失败和同条件修复后通过的例子；以发布门槛判定通过，原始观测作为证据保留。

## 仿真覆盖与上机边界

| 故障层 | 注入条件 | 可观察的判据 |
|---|---|---|
| 任务与工具 | 模型暂不可用、非法工具；错误操作 ID、证据缺失、截断回执；幂等重投、相同来源冲突 | 请求次数、实际副作用次数、是否误报成功、原任务或子任务身份、最终错误码 |
| 运动 | 激光中央缺束、量程或几何异常、无时间进展、错 frame、采集时间错位、单调时钟超时、控制进程消失 | 真实网关何时发零速、Action 如何终止、Gazebo 独立世界位姿的余行及停稳窗口 |
| 场景 | 室内外往返、限制区、未知/重名地点、旧 ROS 委托、场景解释与实际激光冲突 | 地图版本、是否通过指定门口、目标误差、两次回放是否重复执行 |
| 观测与历史 | 激光全无效、发布持续但源时间冻结、仿真时钟回退、JSON 非有限数、断流、消费者中途截断 | 地图年龄与来源、旧数据是否迁入新世界、下一条事件是否仍可读取、恢复后归档数量 |
| 整机软件与交互 | 浏览器桌面/手机布局、加载任务目录、事件视图、停机重启、ARM64 硬件镜像 | 实时数据可见、同一任务可追溯、无传感器时不会伪造位置、合成观测能在板端软件入口读到 |

**上机前需单独验收**：传感器校时和外参、最小探测距离、实际制动距离、底盘急停、掉电后存储和控制器对账、NPU/GPU 驱动、热降频以及长时资源增长。仿真中的停止距离只能用于同一模型的版本对比。当前证据不包含物理 RK3588 或 Jetson 的现场测量。[板卡验收手册](../architecture/board-validation.md)
