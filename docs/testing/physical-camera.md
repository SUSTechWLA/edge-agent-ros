# 物理轨道的相机交接实验

实验回答一个具体问题。机器人收到“采集一帧图像”后，如果采集进程、验收器或控制进程在不同时间断开，谁能够确认已经采过，谁有权再接管相机？

| 所有者 | 可见输入 | 可产生的证据 |
|---|---|---|
| Agent | 用户文本、受部署授权的工具目录、计划步骤 | 保存原 plan、provider 版本和 operation_id。混合计划先为全部已选步骤冻结绑定，再开始派发。 |
| physical-controller | Agent 的冻结请求、持久设备记录、三个分离的 Unix socket | 在同一数据库事务授予资源租约，记录 epoch、boot、版本、在途数。状态未知时保存原证据，禁止用另一版本重做。 |
| physical-camera | 私有传感域发布的原始 ROS Image 和本角色 socket | 核对租约和本地最高 epoch 后读取一帧，将原始 CDR 字节与原操作关联，提供候选摘要。 |
| physical-verifier | 只读帧产物、源端独立见证、ROS 图及本角色 socket | 独立核对采样戳、内容、来源和帧格式，报告通过或反证。交接时另行观察驱动仍可用且旧订阅安静。 |
| 部署操作员 | 已审查的描述符、镜像、资源分配、停止收据、旧容器退出观测 | 通过部署命令执行 drain、核实独立停止证据、释放租约、核对旧进程停止，再启用下一版。 |

工具 `capture_camera_frame` 的参数是空对象。新计划同时保存工具与验收者身份，重复轮询只读同一操作的结果。生产中的设备所有者需要保证私有传感域、设备映射、见证来源彼此独立。此试点的资源是单台相机的采集适配器；底盘准入继续由 Core 和 Gateway 负责。

仿真驱动通过单独的测试 overlay 发布真正的 ROS 2 消息并独立写见证。开发机实验采用隔离 Compose 项目、临时卷和固定本地镜像。测试驱动、伪帧与测试权限排除在板端投影之外。真实相机验收需由现场驱动提供相同格式的源端见证，记录设备序列号、时间域和停采延迟。没有设备独占与独立见证时保持 observe。

复测时从仓根运行 `python tests/system/physical_camera_acceptance.py --image <本次构建镜像> --out <新报告路径>`。用 JSON 中的任务号沿 Agent 的 dispatch、设备侧租约、候选帧、独立判定、结算和交接顺序核对。冻结中、等待证据中、明确失败与结果未知需分别记录。

### 现场驱动需要提供的见证

现场驱动把原始 `sensor_msgs/msg/Image` 发布到站点登记的话题，并独自写入 `/witness/source.sqlite`。将该卷只读挂给验收器。每帧保留 `frames(digest,source,frame,stamp,width,height,pixel_sha)`，分别是规范化 CDR 的 SHA-256、设备来源、frame_id、ROS 纳秒时戳、宽、高、原始像素 SHA-256。驱动还要更新 `heartbeat(singleton,source,last_seen)`，其中 singleton=1，last_seen 是同一台 Linux 主机的单调纳秒时间。完整驱动侧样例在 `tests/system/physical_camera_source.py`。普通 RealSense 驱动只发布图像时，还需要集成这一见证出口。采集器没有见证卷写权限。

独立验收先比对原操作的帧产物，再核对源端像素和时戳。缺失源记录时等待，明确反证时拒绝。交接需要先排空，再由控制器发起新一轮带 `stop_id` 的停采挑战。验收器在源端持续发新心跳的窗口内确认原采集订阅消失。最后由部署侧核对原容器身份和退出记录。设备掉线本身不能证明它已停采。

### 开发机复测

首轮容器启动发现 ROS Node 的只读 `handle` 与成员命名冲突，修复后注入真实订阅。第二轮发现 CDR 对齐填充可导致同一帧的摘要不同；规范化填充后，用源端独立像素摘要与解码结果交叉检查。原失败保存在 `.ci-results/sdd-045/p2/camera-a01.json` 和 `camera-a02.json`。第三轮完成 19 个阶段，包括验收器掉线、采集进程 SIGKILL、未知结果保留和旧版本退出。账本单测另验证了拒绝预先生成的停采证明、持久化失败时不授权采集，以及错域、错误设备与陈旧租约的拒绝。
