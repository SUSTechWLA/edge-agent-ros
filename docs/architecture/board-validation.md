# 边缘计算单元部署与真机验收

本文是 Edge Agent ROS 的目标设计与试验规程。RK3588 和 Jetson 的整机实测结果待填。读完后，你应当能给一块新板选择软件栈、判断哪些服务可以重启，并通过试验回答一个具体问题：**当推理占满资源、传感器拔掉或云端断开时，机器人还能否按约束完成或结束当前动作？**

## 1. 一台机器人需要部署什么

以一台有激光雷达和相机的轮式车为例。车接到“到门口检查通行情况”的子目标时，车上 C++20 任务内核记录任务，推理插件提出操作，执行端校验条件后通过 C++ `rclcpp` 适配器提交导航 Action。导航的反馈来自本机控制栈。相机图像由感知插件就地消费，任务日志保存带时间、坐标系、标定版本的观测与证据引用。将车换成机器狗时，可以替换导航和姿态适配器；原先轮式车的“停稳”判据也必须换成该平台可观测的安全状态。

| 部署边界 | 装载内容 | 运行职责与失效语义 |
|---|---|---|
| 主机 BSP 与控制器 | 厂商内核、设备驱动、时钟服务、平台控制栈、独立看门狗或飞控 | 持有最终运动限制和硬件保护。平台须预先定义失联、控制看门狗超时及电量不足时的行为；飞行平台的安全行为须由飞控结合飞行状态决定。 |
| Edge 核心容器 | C++20 任务内核、能力注册表、任务日志、少量结构化观测、版本化本地进程接口 | 根据设备健康和模型能力接受子目标，持久化动作意图并关联执行结果，重启时先与执行端核对遗留动作。 |
| ROS 与能力适配进程 | `rclcpp`、Action 客户端、传感器/执行器桥、帧变换或感知适配 | 每个能力有版本、健康状态、授权资源和动作完成条件。适配进程可以同一镜像拉起；容易故障或独占设备的适配器单独监管。 |
| 推理进程 | RKNN、RKLLM、TensorRT 或通用模型 API 的提供方 | 在预算内产生结构化提案或感知结果。输出仍需校验。推理进程崩溃或模型切换时，控制器与本地动作监督继续运行。 |
| `linkd` | 出站 mTLS gRPC 客户端、重连、任务与事件同步 | 跟 Brain 交换能力、子目标、确认和结果。断网时保留已确认接收的任务与待上传事实，执行范围由授权期限和离线策略决定。 |

一个服务进程可承载多个同故障域插件；隔离单位按设备权限、故障影响和内存成本确定。实机闭环由各平台的控制器承担。ROS 2 Action 已区分目标受理、执行中、取消中及终态，因此应对“收到取消请求”“动作结束”“平台进入约定安全状态”分别打点。[ROS 2 Action 协议](https://design.ros2.org/articles/actions.html)

## 2. 选板卡、镜像和模型

| 项目 | RK3588 | NVIDIA Jetson |
|---|---|---|
| 实机身份 | 记录整板型号、RAM、存储、散热方式、BSP/内核、NPU 驱动及用户态运行库。不同厂商的 RK3588 板载接线、内核和设备节点可能不同。 | 记录模块与载板型号、RAM、JetPack/L4T、GPU 驱动、CUDA/TensorRT 版本、散热与功耗模式。 |
| 模型产物 | 常规感知网络在开发机转换成目标 `.rknn` 后交给板端运行库。生成模型另走 RKLLM，仅启用已验证的模型家族、量化格式和运行时组合。 | 在目标平台兼容的栈上编译或验证推理引擎。以 Orin 的 JetPack 6.2.1 为可复现示例，它配套 L4T 36.4.4、Ubuntu 22.04 和 TensorRT 10.3。其他型号应分别选取受支持的栈。 |
| 容器设备 | 在 BSP 中识别实际设备节点和设备组，仅把需要的 NPU、相机或串口交给对应适配器；在相同设备映射下运行厂商最小推理样例。 | 使用与 BSP 配套的 NVIDIA 容器运行环境向推理进程暴露所需 GPU/运行库。在同一镜像内验证 GPU 可见、模型能加载、样本能完成推理。 |
| 最低可用能力 | 无合格本地生成模型时，可使用确定性技能和已验证的轻量感知；允许联网且策略批准时可使用远程计划提供方。 | 使用同一能力契约。GPU 配额、内存或热余量不足时，可以换成本机已验收的小模型，或仅执行已批准的有限技能。 |

Rockchip 把开发机转换工具与板端运行时分别发布，RKNN 与 RKLLM 是两条独立的工具链。镜像清单应锁定依赖和镜像摘要，模型清单单独记录模型哈希、转换工具、量化方法、目标后端及适用输入范围。Jetson 的示例版本用于再现试验，选型时需结合实际模块和维护周期。[RKNN Toolkit2 固定版本](https://github.com/airockchip/rknn-toolkit2/blob/2c723177a94fac65cbc036d722907ddbc91980cf/README.md)、[RKLLM 固定版本](https://github.com/airockchip/rknn-llm/blob/f7390530443bf84f0394255a449d7cbe81e69d1c/README.md)、[NVIDIA JetPack 6.2.1](https://developer.nvidia.com/embedded/jetpack-sdk-621)、[NVIDIA 容器运行环境](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)

### Docker 映射约定

以下是拟定的容器内路径。宿主目录由安装清单显式填写，稳定设备别名由板端配置提供。

| 容器资源 | 分配给谁 | 验证方法 |
|---|---|---|
| `/etc/edge-agent` 只读、`/opt/edge-agent/models` 只读 | 核心及相应插件分别可见其所需配置或模型 | 校验清单版本、哈希、模型输入格式；启动日志记录版本。 |
| `/var/lib/edge-agent` 本地持久卷 | 核心日志服务；SQLite 数据库及其 WAL、SHM 文件位于同一目录 | 重建容器后检查记录与未确认事件。验证真实文件系统的同步语义；写敏感动作意图时使用已验证的持久化策略，如 WAL + `synchronous=FULL`。 |
| `/var/lib/edge-evidence` 有容量上限的证据卷 | 由获授权的证据写入/读取进程使用 | 高低水位分别控制原始样本留存与清理；验证留下的证据引用可解析，已淘汰的证据显式标记。 |
| `/run/edge-agent` 本机临时 IPC | 指定进程使用受权限控制的 Unix socket | 容器重启后重新握手；协议主版本、提供者实例和能力代次须校验。 |
| 目标 ROS 2 通信路径及所需设备、GPU/NPU | ROS 桥或设备提供者 | 逐项确认所在域、发现、QoS 匹配、发布/订阅、Action 反馈；需要控制独占权的设备只能交给它的执行提供者。 |
| 设备身份与根证书只读挂载 | `linkd` | 证书过期或对端身份错误时停止同步、记录原因。每台机器人有独立身份；保护凭据的挂载和读权限。 |

运行时对推理和日志等高开销进程设定 CPU、内存以及磁盘预算；测试预算触顶时核心和控制器是否仍有资源。数据库单一服务负责写入；对上行事件和动作意图在同一本地事务中记录相应业务状态。WAL 依赖同机文件系统，离线备份要采用一致性快照或 SQLite 备份接口。动作意图与硬件执行间仍有崩溃窗口，应靠执行器查询与现实观测完成对账。[Docker 资源约束](https://docs.docker.com/engine/containers/resource_constraints/)、[SQLite WAL](https://sqlite.org/wal.html)、[SQLite 同步设置](https://sqlite.org/pragma.html#pragma_synchronous)

## 3. 从开机、失联到恢复

1. **平台保护先就绪。** 供电后由控制器进入设备定义的安全状态。给主机看门狗、ROS 控制器和模型进程分别登记责任与超时，确认主机软件重启时控制器能独立执行平台保护。
2. **恢复本地事实。** 核心读取身份、配置与日志，标识本次启动实例，恢复待上行事件；根据动作 ID 向执行端查询上一次未终结动作。若日志显示“已发送”而设备无法确认，标记结果未知、保留相关资源并请求观测或人工核对。
3. **发现并验证能力。** 适配器激活前探测设备、版本、数据新鲜度及前置条件。一个摄像头插入后，先确认稳定设备身份、测试帧、标定和时钟，再发布能力新代次。相机拔出时撤销能力，依赖本相机的观测步骤进入降级或暂停；其他可独立执行的任务继续。
4. **恢复云边会话。** `linkd` 主动连 Brain，交换能力快照、已确认游标和在途任务。重复消息以稳定 ID 去重；过期授权、旧的提供者代次和过期子目标不能恢复执行权。网络隔离时根据最后一次有效授权执行，超出预算则转入平台已配置的离线行为。
5. **先保护控制预算，再调整计算负载。** 监测核心回调延迟、温度、内存及推理队列。按板型配置进入/退出阈值及持续时间。先丢弃过期感知帧、限制新推理并发，再切换经验证的小模型；当安全所需感知也无法达到新鲜度门限，立即将受影响能力设为不可用并施行对应的安全策略。恢复时通过健康探测并保留滞回，防止能力反复上线。

**时间也是一种输入。** 采样时间、接收时间和处理完成时间分别记录。设备会话包含时钟域及其误差估计；跨设备的数据先映射到共同时间域，误差超出融合窗口时拒绝联合推断。看门狗和本机超时使用单调时钟并关联启动实例。仿真同时检验 ROS 时间暂停或回退时动作是否错误重复、旧观测是否误用。[ROS 时间设计](https://design.ros2.org/articles/clock_and_time.html)、[ROS 2 QoS 官方文档](https://github.com/ros2/ros2_documentation/blob/d21e8d05fbca1ad23d6f2cac6be0d4aa2d8c18ed/source/Concepts/Intermediate/About-Quality-of-Service-Settings.rst)

## 4. 可重做的试验与通过条件

先在软件 Edge 仿真验证状态机，再在板端接回放传感器压测，最后在受控场地做带独立停止手段的真机试验。为每块板登记基线与候选清单。使用相同任务、数据集、随机种子（适用时）、环境温度区间和电源模式，分别记录空闲、典型、峰值与故障恢复四种负载。模型评测保留每个场景及失败样本；同一任务的多次重试应保留原始尝试计数。

表中 `D_control`、`D_safe` 和 `A_sensor` 分别是该机型批准的控制周期截止时间、安全状态到达时限、观测最大允许年龄。由机型负责人按控制周期、响应距离、传感器频率与现场边界填写数值，并在试验前冻结。不同机型的安全状态要给出可被独立观测验证的定义。

| 编号 | 准备与故障注入 | 必须采集的证据 | 通过条件 |
|---|---|---|---|
| B01 冷启动 | 正常启动、无云启动、拔除可选传感器启动 | 控制器就绪时间、首次能力清单、本地/云会话状态 | 未验证能力不能被领取；离线可用范围与本机策略一致。 |
| B02 动作闭环 | 领取同一子目标，分别在受理前、执行中、完成后申请取消 | 任务/动作 ID、全部状态、控制器反馈、独立安全状态观测 | 每条路径有一致终态或明确的未知状态；执行中取消导致机型规定的安全状态且满足 `D_safe`。 |
| B03 传感器热插拔 | 动作中拔插依赖的相机，随后换入不同标定的设备 | 设备身份、能力代次、最后样本年龄、恢复探测、任务处置 | 旧代次或超出 `A_sensor` 的观测无法满足新步骤；恢复前完成标定和时间检查。 |
| B04 断网与重发 | 阻断云链路直至授权到期；恢复后重复发送同一任务与回执 | 出站游标、授权持有者、离线决策、动作 ID、对端确认 | 授权过期按策略处置；重连后双方任务状态收敛，实物动作无重复。 |
| B05 进程崩溃、掉电 | 在写意图后、目标受理后、结果记录前分别终止相关进程；在可控台架上执行断电恢复 | 重启实例、恢复查询、执行器记录、外部状态证据、日志完整性 | 已确认动作不重复产生副作用；不可确认的动作保留未知状态和阻断原因。 |
| B06 高负载与热降级 | 同时运行相机、雷达、推理、日志；在板卡额定范围内逐步增加负载 | 控制回调间隔与最大值、`D_control` 违约次数、队列长度、温度、降频、功耗、内存峰值 | 控制指标符合机型门限，推理并发受限，过载后出现可解释的降级和恢复，保护进程无 OOM。 |
| B07 时钟与坐标系 | 注入异常采样时间、时钟域偏差、缺失坐标变换，仿真暂停再回退 | 采集/接收时、误差、坐标系、拒绝原因、单调时钟超时记录 | 陈旧帧及不兼容坐标不参与联合决策；看门狗按真实经过时间处理。 |
| B08 模型更换 | 使用同一批子目标对比远程、本地和故障提供方，注入超时、畸形输出与能力缺失 | 模型哈希、首个可用提案时延、合法提案率、后条件通过率、任务成败 | 模型替换无需改任务协议；无效提案未执行；候选在预注册的质量/延迟预算内。 |
| B09 长时运行与磁盘压力 | 完成热稳态后按项目约定时长连续执行任务，并受控耗尽证据卷 | 磁盘水位、WAL 大小、丢样数、资源增长、物理动作意图提交状态 | 非关键证据按策略淘汰并留痕；无法持久化新的关键意图时，拒绝启动新的有副作用动作，同时保持平台保护能力。 |

### 报告如何交付

每个试验保存一个运行编号、一份环境清单、一份事件追踪和独立输出（例如控制器记录或相机测得的停止状态）。环境清单至少包含 Git 提交、镜像摘要、板卡与载板型号、内存、驱动、模型哈希、功耗档、散热条件、输入数据版本、阈值与有效试验次数。Jetson 可用 `tegrastats` 记录资源使用和热状态；RK3588 按所选 BSP 可用计数器记录并声明计量来源。若比较两块板的能耗，可使用同一边界与采样频率的外部功率计。[NVIDIA tegrastats 参考](https://docs.nvidia.com/jetson/archives/r36.4.4/DeveloperGuide/AT/JetsonLinuxDevelopmentTools/TegrastatsUtility.html)

用“达到现实后条件的任务数 / 所有已接受任务数”报告端到端成功率，单列拒收、超时、人工接管与未知结果。给延迟指标同时报告样本数、p50、p95、p99 和最大值；样本太少时列出原始值。控制与安全试验逐次判定是否越过硬时限，不能用平均值覆盖一次违约。升级时在同一测试集比较基线与候选，记录成功率差、尾延迟差及资源余量。每个结论标注来自仿真、板端回放或真机现场，使后续团队能够判断证据适用范围。
