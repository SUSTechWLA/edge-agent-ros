# 物理插件如何交接一台正在工作的机器人

P2 已实现相机采集的交接。`capture_camera_frame` 从 ROS 2 读取一帧，独立进程对照驱动侧见证验收。它适合在机器人首次上电时验证版本固定、租约和结果未知的恢复路径。下文的 `navigate_place` 展示同一协议用于执行器还需要哪些保证。底盘的控制权继续由现有 Core/Gateway 持有。相机的停采证据不能证明底盘停稳。[相机试点与故障复测](../testing/physical-camera.md) · [双轨验收计划](../testing/plugin-tracks.md)

## 1. 从一次导航找到四个实际所有者

假设任务 ID 是 `visit-7`，第一步的目的地是已标注的“庭院”。下表中的操作身份采用现有代码的生成规则。

| 谁负责 | 输入、实际动作与持久状态 | 能证明什么 |
|---|---|---|
| Agent 任务执行器 | 把目标编排为 `navigate_place(place)`；在步骤账本冻结工具版本和 binding，记录 `dispatch` 后，以 `visit-7/step/1` 调 HTTP Provider。对候选结果执行该步骤配置的验收策略。 | 工具被选择、下发或结束；出现超时仍能沿原操作查询。Agent 持有用户任务的终态。 |
| Scene Provider | `POST /navigate` 读取目的地和新鲜的融合定位。依据标注场景的通行图生成路点，在 `routes.db` 保存 `op → place + plan`，其中包含场景 revision、digest、frame、路径和坐标；发送前持久化 `sent`，受理后落为 `bound`。 | 相同 op 重入时复用原路线。已有 `sent/bound` 却查不到 Core 记录时返回 `scene.mission_unaccounted`。同一 op 更换目的地会触发 `scene.operation_conflict`。 |
| C++ Core | 通过 `/edge/submit_mission` 接收 mission ID（本例与步骤 op 相同）及有序路点。Core 账本串行占用底盘，逐点生成 `visit-7/step/1/waypoint/1` 等 Action 操作。相同 mission ID 及路点可取回已有状态；路点不同时拒绝。 | 哪个 mission 占用底盘、哪个路点已下发、哪几个路点获得了动作结束后的实测到点证据。Core 的取消受理和最终停稳是两个时间点。 |
| 运动 Gateway 与平台控制器 | 仿真 Gateway 接收 `/edge/navigate_to` Action，用 `/edge/active_operation` 检查 Core 的操作心跳，经 `/cmd_vel` 发速度。根据里程计、配置的激光检查和制动观测返回动作结果。板端部署需要现场控制器实现相应契约。 | 运动是否实际进入执行、制动后是否取得连续静止观测。Scene 另检查 Core 返回的有序证据数量和与每个原路点的距离，当前容差为 0.12 m。 |

当前 Scene 的地点导航 Tool 清单声明 `effect: idempotent`，同一个操作能重入，不代表它具有只读权限。可对照 `preview_route`：后者计算候选路线，前者会委托真的运动。两者即使由同一服务进程实现，在候选验收和运行授权中也应分开。`scene/plugins/navigate-place.json` · `scene/plugins/preview-route.json` · `agent/service.py` · `scene/provider.py` · `src/edge_core/src/core_node.cpp` · `src/edge_gateway/src/edge_gateway_node.cpp`

## 2. 绑定软件版本与排他控制分别解决什么问题

既有 Tool binding 对工具 ID、版本、参数、effect、endpoint 等选定字段求摘要；Service binding 对去掉 `draining` 的清单身份及其依赖求摘要。受管发布还用旧版 revision 做比较并交换（CAS）。它们可分别发现“旧步骤的工具变了”“服务依赖变了”“并发发布让旧版预期过期”。同一 URL 背后换了镜像，需再核镜像摘要。目录中的 draining 只控制新发现；物理交接还要冻结新委托并查清执行端是否仍可能接受旧命令。`agent/planning.py` · `agent/runtime_plugins.py` · `agent/plugin_manager.py`

**v2 的 fencing（拒绝过期持有者）**使用每台设备、每个排他资源单调递增的代数。设 `rover-01/base` 当前代数为 17。即便旧进程恢复网络，上一代延迟到达的速度、启动、续租或重新执行请求也不能驱动已交给第 18 代的底盘。现有 Core 的单数据库文件锁和 `exclusive_base` 唯一索引保护该数据库中的活动 mission。现有 Gateway 的已见操作集合、运动抑制以及操作心跳保存在进程内，心跳报文只携带操作 ID。多个控制进程连到同一底盘、使用不同数据库或复制旧卷时，还需要设备侧的持久 fencing。`src/edge_core/src/ledger.cpp` · `docs/architecture/board-validation.md`

### v2 在哪里执行检查

1. **控制权以本机物理资源为单位。** Core 作为可信命令入口记录原 mission、步骤、资源与授权；最后能让电机运动的受信控制器或独占命令适配器负责兑现授权，并持久化已接受的最高代数。若底层只收普通 Twist，应把唯一可写的命令链路交给这个适配器，并在设备驱动、ROS 授权和部署权限处阻断其他写入路径。现场做不到独占时，只开放路线试算。
2. **把批准对象冻结在执行记录里。** 对新操作绑定 robot/资源、Provider 身份及镜像摘要、Tool/Service binding、原 operation ID、路线摘要和授权代数。同一代、同一动作、同一内容重投只返回原接收结果，内容变化即冲突。动作开始、继续、续租均由末端核对当前已鉴别的持有者、代数、顺序和本地有效期。部署者批准某个镜像不自动授予该镜像所有机器人或全部设备路径。
3. **控制时效用设备的单调时钟。** TTL 由接收端计时；时间同步只用于关联证据。过期后本地进入平台定义的安全过程，中断续租后再收到同代迟到的旧包不能恢复运动。设备重启先禁止运动，核验其持久代数、未决操作和实体状态。卷回滚、记录损坏或无法证明代数单调时要求现场重新建立可信控制状态。代数标识新授权，旧版本镜像回退也必须领新代数。
4. **始终保留独立的现场安全通道。** 急停、本地限速与驱动看门狗由现场控制链持有，控制权交接、网络和 Agent 的可用性不应削弱它们。远程“急停请求已收到”用于定位过程，解除禁止需要物理状态与授权证据。本文的停车判据用于地面车；其他机型必须先定义自己的安全状态及见证来源。

### 三项安全能力与原操作账本如何共同决定准入

本试点应声明 `kind=tool`、`class=physical`、`runtime=process`、`effects=actuation`、`hot_reload=false`、`drain_required=true`，关联 `device_lease`、`stop_protocol`、`verifier`、`operation_ledger` 四个非空引用。前三项定义租约、停车和独立验收，第四项提供按原操作查账的持久接口。受管发布与冷启动/重载都检查声明及依赖，因此直接放入文件也须经过相同门禁。运行时再判断现场资源、健康和授权。在试算或安装时验证接口，不提前分配真实底盘。下列输入和回执是 P0 对运行行为的要求。[v2 描述符与发布协议](../plugin-descriptor-v2.md)

| 运行行为与所有者 | 最小输入 | 必须返回或持久化的凭据 |
|---|---|---|
| 获取/续租/撤销，由设备可信入口执行 | 请求 ID、robot 与资源、经鉴别的持有者、预期代数、已冻结的 provider/binding 和申请的有效期 | 设备持久记录的资源、持有者、当前代数和有效期；竞争同一资源拒绝 `plugin.lease_conflict`，已撤销或代数不符拒绝 `plugin.fence_rejected`。 |
| 停止原动作，由控制器接受、由机型见证确认 | 原资源/代数、mission 和活动 waypoint、原因、停车期限与机型证据契约 | 首先返回“已受理”，再返回“已证实安全”或“无法确认”。列出源、采样数、采集/接收窗口及末态。未确认记 `plugin.stop_unconfirmed`，原子系统诊断作为原因保留。 |
| 验收结果，由与运动 Provider 分离的验收者决定 | 原 op、冻结的目的地/路线摘要、候选结果、独立观测源和已固定的验收者 binding | 关联同一资源/操作的判断、观测窗口、时间域和证据引用。缺失、绑定错误、提供者自签、过期或跨任务证据拒绝 `plugin.verifier_invalid`。有足够证据证明“没有到点”应记录为任务验收失败，与验收器本身不可用区分。 |
| 查询原操作，由 Scene 与 Core 分别读自己持有的账本，对外提供持久查询结果 | 原任务/步骤/waypoint、冻结的 binding 与路线摘要 | 返回最后已提交的阶段、实际受理方、一次副作用的结果/未知状态及证据引用。原操作不存在但不能证明从未派发时保留待对账。 |

声明或授权失效时，禁止新的有副作用操作。已受理动作的停车/查询由已建立的控制端口处理，不能因验收器掉线而把运动搁置在无人监管的状态。运动能否开始、任务结果能否判成功、控制权能否转给另一实例，分别在各自边界上判定。

**同协议可推广到原始传感器。** 例如采集节点直读相机设备时，交接资源是相机，停止协议要求旧进程停止采集、关闭句柄并确认流静默；验收方核对旧实例不再输出、无丢失归属的未决操作及新源能提供有效的新帧。引用已发布的经授权观测事实可以交由 soft 插件读取。将 `preview_route` 独立封装为 soft 时，也要检查进程、挂载及可达通信链路，确保它只能消费已授权事实并计算路线；与有运动权限的 Provider 混装时，部署按 physical 管理。[运行时职责映射](../plugin-runtime-mapping.md)

## 3. 从旧版切换到新版的操作顺序

以下为目标协议的动作含义。当前仓库提供 v1 路线持久化、Core 查询/取消与 Gateway 停车见证；下表的排他授权、持久代数、交接记录及设备校验需在后续开发和台架验收中落地。

| 步骤 | 谁发起、输入是什么 | 输出与继续条件 |
|---|---|---|
| 1. 建立交接记录并排空 | 受信部署端用一次交接请求 ID，提交设备资源、预期旧 binding/镜像/代数、候选 binding/镜像和批准凭据。按资源 CAS 建档；在物理命令入口停止接受新运动任务。旧任务可按原身份查询、按现场策略运行至终态或取消。 | 旧版仍占用本资源，候选仅可做隔离试算。依赖发生变化、请求 ID 复用时内容不同、仍有第二条驱动路径，均不能进入启用。 |
| 2. 按原 ID 对账 | Agent 枚举原在途步骤；Scene 提供冻结路线；Core 返回 mission、活动 waypoint 及状态；Gateway/驱动提供明确的制动回执和独立观测。中途取消仅针对原 mission，不复制或修改原委托。 | 终态、路线与原操作一致，并能证明平台已进入安全状态。控制器终态 UNKNOWN、仅见到取消 ACK、观测不足、执行层账本缺失，均保持禁止新运动并登记人工介入。 |
| 3. 撤销旧授权 | 可信控制端请求末端以预期旧代数关闭运动，在物理资源上持久化更高代数和“尚无可动持有者”；使用交接请求的稳定身份取回同一回执。 | 拿到设备端回执，且过期持有者的命令被末端拒绝。无需依赖旧进程自称已退出；未收到设备回执时维持排空、查原请求。 |
| 4. 停止旧进程，安装并核验新持有者 | 部署端须先读到步骤 3 的租约释放和旧代封闭回执，才可停止旧进程；记录退出结果，再核实新镜像、权限、ROS 命名空间和批准范围。设备端用预期当前代数将新持有者绑定到该资源。批准之后先验证观测、停稳和拒绝旧命令，再放开新任务准入。 | 只有经批准的新实例能领取后续任务。旧任务仍按冻结的版本和身份读历史；已中断任务若需要重新规划，先结清旧动作，另行批准新的有因果关联的操作。 |
| 5. 回退或重启恢复 | 依据交接请求、原操作和物理资源读取已提交阶段。回退到旧镜像也走同一交接流程；重发请求先核对原回执。 | 例如代数已升、发布进程崩溃，新实例核验“无持有者”后才能继续步骤 4。若登记与设备相互矛盾，冻结资源和候选，交由现场处置。 |

在步骤 2，仿真 Gateway 的既有参考门槛是至少三帧静止里程计，采集和到达两个时间跨度都达到 300 ms，速度小于 0.025 m/s 且偏航角速度小于 0.05 rad/s；等待超过 3 s 会报告未确认并抑制运动。发出零速度、看到单帧零速或收到 HTTP 200 都不足以确认停稳。真车应依据机型、载荷、制动距离、独立传感器与硬件急停实测决定门槛。滑动或架空时仅凭轮速无法确认车体已经静止。`docs/specs/SDD-036-stop-evidence.md` · `docs/architecture/board-validation.md`

## 4. 准入、故障和介入

| 场景 | 谁作决定 | 对现场系统的作用 |
|---|---|---|
| 模型、自动工具作者、Session 或 Watchdog 想发布运动插件、修改路线、解锁、换代或直接调用速度端口 | 权限由部署方和设备命令入口落实。观察者可发诊断事实或提案，开发候选可在无驱动权限的沙箱做试算。 | 拒绝未授权物理副作用，记录请求来源与拒绝原因。EventBus 消息、镜像标签、注册成功、模型判断均不能充当执行授权。 |
| 旧操作已冻结，但清单变更、Provider 路由漂移或验收服务换版 | Agent 要求原 binding，Scene 核对原路线与 Core 记录；验收者按原服务 binding 对账。 | 可读历史，保留原操作。新提供者不能把旧的超时当作“从未执行”，不能用另一个 ID 绕过未知状态。当前相关原码包括 `tool.binding_unavailable`、`verification.binding_unavailable`、`scene.mission_unaccounted`。 |
| 旧实例恢复、相同代的另一实例请求、重复续租、更低代数或延迟运动命令到达 | 末端资源持有者校验授权，持久状态提供比较基准。 | 拒绝旧持有者的运动并记录 `plugin.fence_rejected`（v2 提议）。读原操作可继续；独立本地急停仍生效。 |
| 取消后无有效定位、停车见证不足，或 Core 重启后仍有未决 mission | v1 Core 会把重启前未决的运行/取消中任务转入 `RECOVERY_REQUIRED` 并保留占用。v2 部署端也须保持物理准入关闭。 | 原始 `navigation.stop_unconfirmed`、`navigation.outcome_unknown` 等代码随证据保留。交接记 `plugin.handoff_unconfirmed`（v2 提议），附缺失项。现场人员先确保车辆处于安全状态，核对原控制器、原操作与车体运动，再按授权恢复。 |
| 系统重启后事件归档不可用，或一次发布收据丢失 | 各所有者查自身持久状态，并以同一请求 ID、同一参数重读收据。 | 归档恢复后按事件 ID 补收。收据缺失、旧设备仍可运动或设备最高代数无法确认时，不开放新运动；可独立运行的软件任务和只读查询继续。 |

交接审计至少能找回 request、robot、资源、旧/新 owner 与代数、软件 binding/镜像摘要、操作及路线摘要、阶段、拒绝码、请求/接收时间、停车证据来源与窗口。涉及的任务记录另保留 task、trace、parent event 和 waypoint operation。EventBus 用于串联已发生的事实；设备命令入口和 Core 账本分别证实控制授权与任务结果。新增 v2 交接码应与现有底层码同时留存，便于分别回答“为什么不准换版”和“车辆为什么没有确认停稳”。`docs/module-eventbus.md` · `docs/plugin-development.md`

## 5. 什么时候可以给首台车开放写权限

| 顺序 | 必做验收 | 可审查的通过判据 |
|---|---|---|
| 仿真 | 先用 `preview_route` 做只读对照，再用 `navigate_place` 执行同一已知地点。注入同 ID 异路线、旧 Provider 消失、动作回复丢失与 Agent 重启。 | 每个预期 waypoint 的物理派发次数可核对；同 ID 异内容拒绝；恢复沿用原路线和 op；独立观测与到点回执一致。现有测试可复用。`tests/system/scene_binding_acceptance.py` · `tests/scene_recovery_acceptance.py` |
| 独立台架 | 两个候选 Provider 竞争同一资源，同时延迟旧命令、暂停旧进程、断网、截断交接收据、重启 Core/Gateway；分别在撤权事务前后和新持有者授权前后断电。 | 同一时刻至多一条可驱动路径，过时代数获准动作数为零，未决或未知停稳后的新运动数为零。重试相同交接请求不产生第二次授权。单独记录被拒动作、末端实际输出、实体见证和恢复所需人工步骤。`src/edge_core/test/ledger_test.cpp` · `src/edge_gateway/test/watchdogs.py` |
| 首台真车 | 场地隔离并启用现场急停，先观测或试算，再以授权地点、低速和限定范围执行。模拟里程计丢失和控制链超时，确认旧发布者被阻断且回退后仍执行较高代数。 | 现场审批绑定确切镜像、设备和能力范围；有机体独立见证、制动实测和介入回执。只能证明“软件栈已启动”、无法在最后命令入口拒绝旧命令、或不能核验实体停稳时，保持只读/试算。 |

交付决策建议先实现并验收场景 Provider 的排空与 Core 原任务对账，再在一个受控的地面车控制器上兑现持久 fencing。第一阶段能显著降低软件换版时重复派发的风险；只有末端拒绝和真机停车均有证据后，才开放跨实例的物理控制交接。
