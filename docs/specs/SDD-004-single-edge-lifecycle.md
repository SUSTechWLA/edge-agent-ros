# SDD-004 · 单台 Edge 的持续任务、自动恢复与人工介入

**状态：待实现的产品规格。** 首个交付对象是一台机器人及其本地工作台。用户从同一自然语言入口查询系统、诊断运行故障、发起现场任务和追问结果。每次请求都应得到可以核对的处理结果，包括完成证据、缺少的能力、待澄清的条件或明确的人工介入请求。单次任务有结束条件；常驻服务可跨任务和重启继续工作。

## 背景与价值

例如用户说“去庭院巡检，到门口如果不能通行就告诉我为什么”。系统需要理解巡检和反馈这两个交付物。机器人发现门口受阻时，提供者应报告传感器时间、障碍观测和停车回执。现有替代路线且它处于授权范围时，可以在确认原动作终态后规划新路线；缺少通路、停稳证据或授权时，应交代机器人停在哪、还缺什么、谁能解除条件。用户可以离开工作台，稍后仍能找回待办和原任务。

| 目前可复核的行为 | 下一阶段的缺口 |
|---|---|
| `POST /agent/tasks` 持久化任务；相同 `trigger.kind/source/id` 可去重。工具清单、模型、提示和诊断均有现成扩展入口。 | `trigger.source` 用于溯源。按真实用户或运维主体授权、关联用户后续追问、只展示其可访问的任务，尚需实现。[任务入口](../../agent/service.py) · [模块术语](../harness-extensions.md) |
| 规划器验证步骤，执行前核对工具版本与绑定。内核保存 ROS 委托，网关根据现场观测制动。确认过的 ROS 动作从账本消失时，系统进入 `RECOVERY_REQUIRED`。 | 端侧需对同一提供者重装、旧设备身份失效、授权过期等情形区分“可同 ID 查询”和“可重新执行”。[规划与绑定](../../agent/planning.py) · [运动验收](../v1/gateway.md) |

## 设计与契约

### 1. 用户能要求什么

| 用户说的话 | 系统如何处理 | 完成证据 |
|---|---|---|
| “告诉我现在装了什么，刚才为什么停车” | 登记只读系统工具，查询能力目录、任务账本和观测记录；出现多个可能的任务时请求用户选定。 | 机器身份、目录版本、选定的任务、原错误码、观测采样时刻。历史读数标明年龄。 |
| “传感器恢复后继续原巡检” | 记录有有效期的条件并订阅恢复事件。执行前读取新鲜传感器和原操作回执，核对权限、抢占与停止状态。 | 条件实际满足的时刻、原任务及操作 ID、重新检查的证据、后续行动及终态。 |
| “每天按这个区域巡检” | 把周期、范围、发起主体、截止条件和失败预算保存为配置；每次触发生成稳定 ID。停机跨过计划时段时按配置跳过、合并或补办，并记录选择。 | 每次执行各自的终态、下次期限、历史漏跑区间，以及撤销后未派发的次数。 |
| “修复运行问题并继续” | 只读诊断先找出失败层。只有当前设备注册了相应修复工具、策略已授权、修复前置条件成立时才调用它；涉及新权限、作用范围变化或现场条件不明时发出介入请求。 | 诊断输入、选用工具与版本、前后健康探针、原任务是否可续办。例如重连只读传感器服务成功后仍要取得一帧新的有效观测。 |

没有执行能力时返回能力缺口及可行的下一步。例如无相机时说明缺少图像采集工具，已有定位信息可单独提供。对会改变现场的请求，模型提供候选步骤，执行层依据设备事实判定是否授权和可执行。用户输入、日志中的文字、模型生成的“已批准”都不能充当批准记录。

### 2. 谁拥有事实，谁能行动

| 模块及开发入口 | 输入、输出与职责 |
|---|---|
| Source / Trigger、任务 Agent | 用户输入、受信主体、配置化条件或 watchdog 事件 → 原任务或关联子任务。复用 `task_id`、`trace_id`、`parent_event_id`，以来源和触发 ID 抑制重投。同一故障连续报警合并到同一未处理请求；恢复后再次发生生成新的故障记录。 |
| Planner / Tool Plugin | 自然语言与已授权、当前可用的目录 → 结构化步骤、期望证据、工具绑定。沿用 dsh 的 Plugin、Tool、Model。系统查询、运行维护和机器人动作分别由对应提供者实现，挂接新工具时执行已有契约测试。 |
| Agent 账本与执行内核 | 步骤、当前策略、参数、动作身份 → 已记录的执行意图与结果。策略由部署方管理；插件声明的 `effect=read/idempotent` 描述行为契约，幂等动作仍可能需要授权。提供者校验授权范围；底盘由 ROS 内核和网关持有执行权。 |
| watchdog 与通知插件 | 超限、反复失败、观测恢复或账本缺失事件 → 可去重的 Trigger 或持久待办。watchdog 可单独启动、停止并续读游标；订阅事件本身不触发物理动作。工作台待办作为本地首个渠道，外部渠道通过独立插件发送。通知失败由该插件补投，机器人动作不随之重放。 |

第一阶段在现有 Agent 账本旁增加介入请求和待通知记录，两者与触发它们的任务事件在同一事务写入。归档保存审计副本。现有 SQLite、HTTP 和 ROS 边界即可承载首版，后续按实际负载拆进程。

### 3. 自动恢复与批准规则

每台机体使用版本化策略配置工具、允许主体、目标范围、风险条件、最长有效期、重试次数和冷却时间。查询、只读恢复探测和已授权的幂等修复可以无人执行。影响共享控制器、机体现场状态或其他任务的操作须按配置申请批准。未授予的能力按默认拒绝处理。批准也不能释放结果未知的设备、忽略陈旧观测或越过网关保护。

1. **记录与分类。** 首个故障写入错误码、层、操作 ID、尝试计数、现场证据及其新鲜度。暂态故障先退避；预算耗尽或遇到动作结果未知时转入相应待办。人同时下发取消时，停止继续调度并核实已受理动作的现场状态。
2. **对账与热替换。** 可查询的动作先向原提供者按稳定 `operation_id` 查收据。计划保存工具版本、绑定摘要及提供者实例或持久账本身份。停用插件后立即停止新领取，允许旧实例在限定时间内完成查询、取消或交还。相同 URL 和版本重新上线仍须证明可查询原账本。确认未受理或幂等重放可由同一账本验证，才可按原 ID 重试；已完成则取原证据。原账本丢失时保留动作未知、隔离对应控制资源，并向人报告所需核查。替换插件不能使旧动作自动转移。
3. **建立请求。** 对同一任务、步骤、故障事件和请求类型建立唯一 `request_id`。请求分为补充事实、批准具体动作、现场核查。保留请求版本、允许的回答、请求主体与可处理主体。将待办投递给任务拥有者或部署指定的当班角色；实际发送使用 `request_id + revision + channel` 去重。区分本地已登记、渠道已确认送达、人已处理三件事。收件方不支持幂等时标出重投可能造成重复通知。
4. **决定与兑现。** 目标接口使用 `GET /agent/interventions` 查询，`POST /agent/interventions/{request_id}/decision` 提交 `decision_id`、请求版本与选择。服务从受信会话取得处理人身份，并校验设备、参数摘要、工具绑定、允许范围、过期时间和当前任务版本。以数据库条件更新决定唯一获胜者。重复相同决定返回第一次结果；同键异参、已拒绝、已取消、旧版本或过期请求返回冲突并附原因。确认消费与动作意图在同一事务落盘，执行仍须与源端核对。状态读回不能验证授权时只允许查询。部署方需给出可信校时要求；本次进程内等待使用单调时间，重启或明显回拨后无法证明仍有效的旧许可转入复核。
5. **恢复原任务。** 收到许可或人工核查结论后重验现场条件、调用结果和资源占用。新的处置方案使用与原计划关联的版本及新的动作身份；原动作身份始终对应原参数。恢复后向发起人发送最终结果、证据和仍未完成的交付物。

**介入请求必须让值班者能行动。** 请求携带 `robot_id/task_id/trace_id/operation_id`（尚未派发时操作 ID 可空）、错误码及来源、最近一次可靠观测与时间、已尝试的方法和结果、当前能确认的现场状态、建议的下一步、可选决定及各自后果、过期时间和安全等待行为。界面应可一键查看证据和原任务。例：“巡检第 2 段的导航回执丢失。最后观测在门口，当前停车尚未确认。请现场核实底盘已停并核对原控制器的委托记录；等待期间底盘保持占用。可提交核查记录或保持等待。”单击“已阅读”只确认送达。

## 验收与证据

以下指标是**拟议的开发验收门槛**。每个阶段先提交白盒故障用例，再由黑盒测试通过公开入口独立观察。记录 SHA、镜像 ID、输入、机体/地图、策略和插件版本、注入时刻、宿主与 ROS 时间域、期望/实际结果及日志路径。黑盒对每个物理结论另收独立真值或实机测量。

| 阶段和编号 | 故障注入与白盒断言 | 本地黑盒通过条件 |
|---|---|---|
| A · AC-1 自然语言和缺口 | 系统查询、运行诊断、现场任务、混合请求各准备五条，并加入同义表达、禁止动作、目标歧义和能力缺失。固定期望交付物、允许工具和禁止副作用。 | 所有只读及拒绝场景产生的物理调用为 0；完成的任务逐项有证据；其余给出可操作的缺口。固定规则与真实模型分别报告，模型评测另报首次正确率、漏步骤数和全部原始失败样本。 |
| A · AC-2 恢复与热拔插 | 受理前、受理后回执前、写终态前依次断开。注入短暂断流、插件换版本、同 URL 换空账本、重复触发和进程重启。统计实际副作用与调用次数。 | 暂态故障在预算内恢复时，原任务完成且人工请求数为 0。结果未知时保留原 ID，有副作用的操作额外执行次数为 0。换插件后新任务可见新目录，旧任务保留原绑定和核查结论。 |
| B · AC-3 主动上报与授权 | 测告警风暴、通知离线、确认回执丢失、双人并发决定、同键异参、超期、时钟回退、取消与批准竞争。对提交前后进程崩溃分别注入。 | 本地在线空闲基线下，从故障判定到待办可见 ≤5 s；离线待办持久保留，重连后可核实送达。单个故障周期仅有 1 个逻辑待办；未授权、过期或重复批准导致的新派发数为 0。拒绝原因与原记录能被查询。 |
| C · AC-4 持续运行 | Docker 单机先做 24 h 混合任务，目标机再做 72 h；记录实际时长、任务数、定时触发漏跑、资源曲线。包含传感器断流、模型不可用、通知断网、重启、磁盘逼近配额和连续热点报警。 | 调度器恢复后所有已受理任务都有终态或明确可查询的待办。无失去证据却报告成功、无重复物理动作。以板型预先冻结 CPU、RSS、磁盘、控制超时和停车预算；超限期间停止新高开销任务，保留关键意图与待办，记录遥测裁剪区间。测得实际时长后填入报告。 |

统计按故障类型分别计数。**自动恢复率**为预先列为可自动恢复并已完成的样本 / 该类全部注入样本。**不必要介入率**为产生人工待办的可恢复样本 / 该类全部样本。还应记录应上报而遗漏的数量、每 100 个任务的人工介入次数、介入耗时和同一动作副作用次数。分母为零时填“未覆盖”。反复重试、降低告警数或延长等待不会计成任务成功。

本地先复用[规划器契约](../../tests/planning_contract.py)、[任务账本测试](../../tests/agent_trace_contract.py)、[故障注入](../../tests/system/agent_faults.py)、[公开工作台回归](../../tests/console_resilience.py)和[单机回归入口](../../tests/system_suite.py)。每项开发只重跑变更模块及其消费方；审批/恢复改变动作授权时同时复测控制内核、制动与取消。可复制的本地结果为主要交付物。远程 CI 失败分为产品行为、环境启动和测试探针问题，保留各自证据。物理门槛按[上板验收手册](../architecture/board-validation.md)执行。

## 迁移与回退

以增量表和版本字段部署，旧任务沿用原状态和回执。旧记录缺少主体或工具绑定时只读查询，并在需要新权限时重新确认。首轮用只读模式计算“若启用将采取什么操作”，对照人工处置后逐类启用白名单。回退时先停止新调度和外发、冻结待批准操作、对账在途动作，保留账本和通知游标。服务重启后从未完成的真实记录恢复。队列容量或审计存储不足时拒绝受理新的副作用动作，优先保留未完成任务、批准记录和执行回执。
