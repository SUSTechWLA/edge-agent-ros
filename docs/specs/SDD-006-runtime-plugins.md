# SDD-006 · 可热插拔的共享服务与独立结果验收

## 背景与价值

在提交 `38fee71` 的隔离相机实验中，提供者返回一个不存在的图片地址，任务仍成为 `SUCCEEDED`。同一版本的巡检能在运动回执之后再用里程计核验位置，但这项判断写在运动内核里。要让开发者或 AI 为一个已有工具增加独立的验收、让多个模块共用同一服务，需要统一的提供、依赖、发现与卸载契约。[原始实验](../evidence/tool-receipt-boundary.json)

## 设计与契约

1. **服务及生命周期。** 受信部署者在现有插件挂载的 `runtime/<id>.json` 放置独立清单。v1 字段为 `schema_version:1,id,version,endpoint,provides,requires`，后两项是服务名数组。清单只引用独立进程，挂载前部署者启动对应进程。运行时读取完整快照，识别缺失依赖、冲突提供者和循环，按安装内容和传递依赖绑定版本。原子发布、替换、移除在下次查找生效。启动、停止进程由 Docker 管理。通过 `GET /agent/plugins` 查看提供者和依赖状态；目录就绪表示声明可解析，网络可达性由实际调用验证。
2. **独立的验收要求。** 声明产物 `outcomes.image` 的工具默认必须用 `verify.image` 验收。可选现场文件 `<EDGE_CONTRACT_DIR>/verification-policy.json` 格式为 `{"schema_version":1,"tools":{"tool_id":["service"]},"outcomes":{"outcome":["service"]}}`。这些规则只增加必需项，可以为已有提供者横向增加检查。发布者对文件原子替换；无文件使用内置规则，存在但损坏应明确阻止新规划。观察者继续使用事件归档。LLM 和工具回执均无权改变已绑定的验收要求。
3. **执行和恢复。** 在计划中保存每步的必需服务，首次派发前解析并持久绑定提供者及其传递依赖。服务缺席时不派发依赖它的操作。工具终态回执是候选，先把候选和“待验收”状态事务性落账，再调用只读验收服务。进程重启、服务离线或版本不符，持有候选的任务只重试验收，不重做原动作。原始调用已发出但尚无持久回执的窗口仍遵循原操作 ID 和提供者的幂等或对账契约。每个通过的验收持久保存；全部通过后才提交 `verified`，原始证据与独立验收证据分别可查询。无依赖的任务使用原路径。
4. **验收协议。** HTTP POST 请求含 `operation_id,task_id,trace_id,service,plugin_id,plugin_version,tool,arguments,outcomes,evidence,started_at`。响应必须回显 `operation_id,service,plugin_id,plugin_version`，返回 `verdict=pass|fail|unknown` 和非空对象 `evidence`。明确反证进入 `BLOCKED`；不可达、未知、无有效回执或版本变化进入有界重试和可续办的待核查。重投同一候选应产生可复查的判断，验收服务无设备执行权。
5. **首批独立插件。** 提供两个可单独启动和卸载的无模型工具插件，职责分别为图像文件可解码性和产物摘要校验，均作为验收服务使用，对模型不暴露 Tool。以受控采集目录、真实小型灰度图为例；文件引用限定在本次操作的产物目录。部署者可以用其他实现处理 JPEG、对象识别或真实相机。机器人内核及 ROS 驱动继续拥有运动授权、制动和设备交接。

## 验收与证据

| 编号 | 输入或故障 | 观察项 |
|---|---|---|
| AC-1 | 在线安装、升级、撤销服务，缺依赖、冲突及循环 | 目录返回可诊断状态，传递绑定随依赖升级变化，其他服务和任务可用。 |
| AC-2 | 真实可解码图像；地址无文件、文件损坏或属于另一操作 | 只有有独立证据的任务成功，保留两种回执、因果事件及版本。 |
| AC-3 | 候选已落账后停止验收器、换版本、重启 Agent，再恢复原服务 | 不因重试或重启再次执行原工具；验收绑定保持，原操作 ID 续办，无关任务继续。 |
| AC-4 | 在相机与 Agent 代码保持不变的情况下加入第二个验收器 | 通过独立清单与现场策略生效；错误摘要造成明确失败，已在途任务保留原规则。 |
| AC-5 | 错操作 ID、错误版本、未知结论、服务超时、重复交付以及旧任务数据 | 无假成功；诊断和续办有据可查，已完成的历史结果可读。旧的未派发步骤按新要求绑定；已派发且缺验收记录的受保护旧步骤保留待人工核对。 |
| AC-6 | 在独立 Docker 上跑软件黑盒和原全量 ROS/Gazebo 系统回归 | 留存版本、镜像、运行编号、每个场景预期与实得；软件模拟与板卡现场测试分别标记。 |

## 迁移与回退

工具清单、事件消费者、现有 HTTP/ROS 任务接口保持兼容。新增的图像成功条件适用于声明图像产物的新任务；没有部署对应验收器时向操作者报告缺失。切换服务版本前先检查有无等待验证的操作，可恢复原绑定后续办。回退运行镜像前先排空活跃任务并保留任务卷备份；旧执行器不能消费新版待验收步骤。历史 `verified` 仍按运行时版本解释。

2026-11-17 补充有序卸载。清单可选布尔字段 `draining`。切到 true 后，该服务及其依赖方退出新操作的绑定；已持久绑定的操作仍可按原摘要取回端点并完成验收。仅改变接纳状态不会改变绑定摘要。目录报告 `draining`；未带摘要的查询返回 409 及 `plugin.draining`。撤下清单或更改实现后，旧摘要不再授权调用。AC-3 增加可复现的“拒接新任务、完成已接任务、随后卸载”场景。

2026-11-17 实现服务目录、按名称或摘要解析、现场策略和独立验收队列。工具终态候选与对应 `tool.response` 在同一 SQLite 事务提交，已通过的验收逐项落账；只读校验通过有界 HTTP 调用。领域逻辑在两个独立进程中实现。复测入口为 `tests/test_runtime_plugins.py`、`tests/agent_verification_contract.py`、`examples/result-verifiers/test_verifiers.py` 及 `tests/system/runtime_plugin_acceptance.py`；由系统测试选择器纳入回归。开发镜像已验证强制停止 Agent 后不重复采集。发布候选以干净提交的全量结果为准。

2026-11-17 AC-5 增补两个回归。现场策略 JSON 嵌套过深时，原诊断目录会再次解析同一坏文件；已隔离错误，并验证修正策略后任务可续办。旧活动任务步骤 JSON 损坏时，SQLite 对出队记录取 JSON 字段可能阻塞健康任务。现在启动时单独保存原文到 `quarantined_steps`，受影响任务挂起并记录 `journal.invalid_steps`，健康任务继续。

| 条件 | 实际证据 |
|---|---|
| AC-1 / AC-3 注册、排空、卸载及恢复 | 传递依赖置为 draining。新查询返回 409，原绑定查询成功；旧拍摄候选续验成功，新任务此时采集次数为 0，无关心跳成功。撤销后旧摘要查不到服务，恢复清单后新任务成功。 |
| AC-2 / AC-4 两个独立验收器 | 有效图片解码为 2 × 2 的 4 个像素；缺文件、旧版无效文件地址、截断和错操作均被阻止。第二个服务通过策略加入同一相机，错误摘要产生独立反证 `digest.mismatch`。 |
| AC-3 / AC-5 重启和协议故障 | 在第二个验收器已收请求、尚未回执时强制终止 Agent。重启后自动完成。第一次已通过的验收调用 1 次，第二次只读验收调用 2 次，原采集调用 1 次。错操作、错版本、未知结论及超时均进入待核查。在另一个慢验收尚未结束时，无关任务实际完成。 |
| AC-5 / AC-6 兼容性与运行平台 | ROS 镜像内 5 组任务账本测试、8 组服务目录和协议测试、Linux 容器内 10 组示例测试通过。AMD64 及模拟 ARM64 硬件镜像验证公开服务查询和缺里程计恢复；ARM64 另跑 5 组验收队列白盒。既有 Qwen 插件作者在此次版本上仍能从故障生成只读候选，重启后新增候选为 0。 |

现场验收需要补充真实相机适配、产物写一次的存储语义、时钟相关性和任务要求的视觉内容。当前的环境证据为合成图像、ROS 传感器夹具及单机 Gazebo。团队复查时，从 JSON 中的 `blackbox.cases.<场景>` 查任务，再用 `calls_by_operation`、`sample_trace` 与 `raw_files_sha256` 回到原始操作、因果事件及本机完整报告。
